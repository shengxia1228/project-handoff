# 交接结构与项目适配

仅在生成或更新交接时阅读。以下是组织内容的参考，不是需要逐项填满的表单。写入 `PROJECT_HANDOFF.md`，保留接手入口，其他区域按项目合并或省略；缺失的关键事实明确标注。

文件开头写项目名称、可靠更新时间及时区、项目根目录或材料位置。已确认的分支、提交和工作区快照放在相关区域，无 Git 时不添加 Git 章节。

## 1. 接手入口

让新 AI 一分钟内找到：

- 当前目标或里程碑。
- 准确停止点，包括最后完成的动作和未完成的连接处。
- 下一项具体动作；若需先解决阻塞，明确前置条件。
- 当前阻塞，没有则简写；无法确认则注明未知。
- 最先打开的少量文件或材料及其作用。

这里只写极简摘要，不重复后面的完整清单。

## 2. 目标与约束

写清用户最终想获得什么、当前里程碑的完成标准，以及明确的行为要求、技术或设计限制、范围边界和禁止改动事项。把用户要求与 AI 选择的实现方法分开；未定义的验收标准不能补成用户要求。

## 3. 当前工作

概述现有实现、文档结构或工作流程，列出会影响接手的已实现成果、进行中工作和停止原因。必要时使用紧凑表格：工作项／实施状态／证据或验证情况。

让“尚未接线”“等待审阅”“仅有提议”等差异一目了然。代码项目可写主要模块与数据流；文档项目写章节进度与未落实反馈；不复制整个任务历史。

## 4. 关键材料与环境

每项只写位置、作用和有效版本。记录主源文件、派生成品、关键输入、依赖清单及继续工作确需的环境信息。必要时包含少量常用命令与执行目录；把已成功执行的命令和待验证的建议命令区分开。

外部文件或服务注明新会话需要的访问方式，不包含秘密。共享链接未验证可用时明确标注。仅存在于当前会话的临时资源、进程或内存结果不能描述为已持久保存。

## 5. 决策与失败经验

保留仍约束下一步的决定、理由和重新考虑的条件。用户明确拒绝的方案不能由 AI 随意重开；AI 自行选择的方案不能升级成用户硬性要求。

失败经验注明方法、观察结果、确认或疑似原因及合理重试条件。无法核实的旧理由保留来源标签；已无关的试错经历省略。

## 6. 验证与阻塞

对重要结论记录验证对象、方法、结果和适用版本或时间；没有这些信息时不要伪造。注明本次检查、旧结果、修改后未复测以及完全未验证的部分。

活跃问题记录症状、相关材料、已尝试处理及当前结果，区分已确认与疑似原因。说明访问不到的材料、缺失的环境或等待的外部条件。

## 7. 下一步

按依赖顺序给出必要的近期行动，通常 3–7 项，有多少明确事项就写多少。把待用户决定的问题、待技术调查的问题和等待外部条件的任务标清；不要为了凑数创建待办。

最后留给接手者一段简短指令：先读取入口材料、核对当前工作区和验证范围，处理存档与现状的差异，再从停止点继续；保留用户目标，遵循新指示，不把计划当完成，不无故重开已解决的问题。

## 不同项目的证据落点

| 项目 | 优先记录的接手信息 |
| --- | --- |
| 代码／工程 | 实现位置、尚未接通的部分、分支与重要未提交改动、测试范围、必要环境和硬件验证情况 |
| 研究／分析 | 原始来源、数据版本、方法、可复查结果、尚未证实的推断和待调查问题 |
| 文档／PPT／设计 | 可编辑主文件与导出成品的对应关系、内容和视觉审阅状态、仍未落实的反馈 |
| 表格／数据 | 原始输入和当前主版本、关键公式或处理步骤、刷新与重算状态、已检查的范围 |
| 纯对话／规划 | 明确目标、约束、已定决定与提议的区别、已知未知项；注明未核实实际成果 |

交接质量取决于新 AI 能否准确继续，不取决于章节数量或篇幅。优先引用已经维护的资料；不要因压缩而丢失唯一保存的约束、决策理由或关键失败经验。
